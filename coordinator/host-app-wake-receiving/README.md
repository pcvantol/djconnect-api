# Host-app-wake receiving components

This source candidate implements closed private DATA codecs, the existing custodian HMAC channel, actual D1 receiving lifecycle/atomic SQL guards, a saved-key assertion verifier/counter writer, a Source181 backend binding, and readonly discovery of one existing operator role. The private HTTP issuer/native/operator and target transport composition is implemented as a source candidate. The first-attestation implementation below is a locally qualified source candidate; genuine Apple enrollment acceptance, public routing and production composition remain open. Source181 remains unchanged.

`wire.ts` defines the exact required fields and bounds. No optional fields exist in these DTOs. All accepted string values are ASCII: identifiers use the declared regex, digests are lowercase 64-character hexadecimal, native SDK key identifiers use canonical standard padded base64, and nonces use unpadded canonical base64url for exactly 32 decoded bytes. Native key decoding permits 1..1024 bytes as a DATA bound only; genuine enrollment must independently select and verify the actual SDK identifier and policy-specific length. The fixture is synthetic and is not an enrolled key. Semantic native registration operation IDs and separate Core challenge IDs are lowercase UUIDv4 DATA; revision is an integer 1..256. Times are nonnegative JavaScript-safe integer milliseconds, with an original wake ceiling of eight hours, an existing display-expiry cap, and a challenge ceiling of 30 seconds. These bounds do not mint a lifetime or establish clock qualification.

The public transcript contains the original Core purpose, immutable semantic registration operation, generation/revision, target, platform, APNs environment, original authenticated context bindings, actual SDK key identifier, actual token-byte digest, and original boundaries. It excludes API authorization, principal, install-token-record, purpose-record, proof-job, capability, and native-key-record identifiers. Core must map its public challenge UUID to the private reserved API job without exposing that job identity.

Signing bytes are UTF8(`DJC-HOST-APP-WAKE-TARGET-REGISTER-V1`) followed by one actual LF byte, followed by the canonical UTF8 JSON object `{original,challenge}`. Object keys are sorted; no whitespace, BOM, normalization, fractional/exponent numbers, negative zero, duplicate or unknown keys, escaped-key alternatives, or extra slash escaping is accepted in the canonical transcript. Plain object decoding remains structural DATA only. `parseNativeTranscript` checks the raw transcript against the independently reconstructed canonical representation; the older shared wire is unchanged. Token SHA256 hashes the original APNs token bytes, never their hexadecimal text. Canonical bytes and SHA256 were generated independently with Python standard json/hashlib/base64 in `qualification/native-transcript-vectors.json` and exercised in actual local workerd.

`operator-auth.ts` uses the actual existing `requireAdminAuth` HMAC implementation, while explicitly rejecting its Bearer fallback. The signed body binds the version, method, route and action because the old HMAC preimage is timestamp + '.' + exact raw body. Authentication alone creates no authorization row or purpose.

The receiving lifecycle retains original grant/challenge bounds and late-auth expiry, never renews original leases after lost replies, and uses the atomic dispatch guard for locally current operator/principal/native/policy state. A synchronous callback cannot establish remote Core currentness. Actual original Core binding preimages, native enrollment/signing policy and qualified original clocks remain mandatory inputs; fixture hashes or a parsed tuple cannot replace them. App Attest environment does not establish APNs signing environment. Existing rendezvous fixed-QA enrollment policy is not admitted as a generic production host policy.

Run `node_modules/.bin/tsc --noEmit --project coordinator/host-app-wake-receiving/qualification/tsconfig.json` and `node_modules/.bin/vitest run --config coordinator/host-app-wake-receiving/qualification/vitest.config.mts`. These checks have no real key, operator, provider, device, deployment or activation effect.

## Persistent receiving lifecycle increment

`receiving-store.ts` now implements actual D1 operator authorization, issuer and native nonce/proof once-history against the existing `install_tokens` table. The selected original semantic purpose is the issuer primary key; a separate unique transport operation and server-owned random claim choose one concurrent winner. Authenticated late requests retain the original expired window. Withdrawal uses retained rows and clears linked Source181 ciphertext without new capacity or send-budget allocation. Rotation does not confer lineage from a new install-token record. Status reads never reconstruct credentials.

Native jobs retain the original nonce, challenge boundary and expected proof kind. The durable proof claim changes the job to private VERIFYING **before** any native crypto await. Negative closure records terminal UNKNOWN, REJECTED or EXPIRED; UNKNOWN cannot become a new verification attempt or be reopened by a positive verifier. Only the same original in-flight VERIFYING claim may eventually publish an actual verified counter receipt. A process crash does not re-run a retained VERIFYING claim. The saved-key assertion writer described below verifies an actual cryptographic proof and atomically advances its enrolled key counter; it accepts no caller boolean or generic parsed proof. The first-attestation source path below is separate from genuine vendor/device qualification.

`dispatch-guard.sql` is a separate source-only trigger at the unchanged Source181 dispatch marker. It atomically joins locally current operator authorization, exact active installation record, issued purpose, verified native job, enrolled key/counter, target, bindings, and identity/deployment-policy records. Missing/withdrawn/retired/changed rows deny the marker. Native key policy here requires canonical standard-base64 32-byte identity, separately from the generic public transcript DATA bound. Genuine enrollment and signed-environment receipt production is still absent. SQLite's own wall clock provides an additional local expiry veto; it does not qualify the original Core/Apple cross-domain clock. Predicates are grouped to respect the measured D1 expression-depth ceiling. Guard SQL exceptions leave the Source181 marker uncommitted; its existing conservative UNKNOWN handling applies. No provider call is made by the store/trigger qualification.

`request-window.ts` captures one original 30-second request window before any await, detects later clock regression, settles cancellation even for an uncooperative supplier, and never starts a new stage after expiry. A mandatory clock supplier remains necessary; this helper does not establish clock qualification. An already started SQL mutation cannot be cancelled retroactively.

`server-wire.ts` and `principal.ts` implement private Core-to-API DTO decoding, strict route selection and actual existing `djci` row lookup. These private DTOs are separate from the owning Core's seven Apple-to-Core proxy DTOs. They never accept forwarded paired app headers, create/rotate an installation token, or issue permission from transport identity. The HTTP components below supply bounded body/auth/dispatcher integration; the first-attestation source path is described below; the qualification worker continues to return 503 and no public route imports these files.

Core proxy operation selection v3/v4 preserves the frozen R31 public transcript. Its request correlation hash binds canonical `["DJC-HOST-WAKE-CORE-REQUEST-V1","POST",exactCorePath,closedBody]`. Prepared/challenge replies must supply immutable expected native proof kind from actual API enrollment/job state; neither app-local key existence nor an old rendezvous journal can choose it. Capture prebody genuine transport/task/window first; decode the bounded body, bind identity to that same lifetime, and latch the actual original child before its first state/API/SQL await. This source does not pretend a body identity can be known before reading the body.

The current SQL gate is split into `eligibility-view.sql`, `registration-guard.sql` and `dispatch-guard.sql`. The registration trigger consumes the exact original verified proof and records the actual Source181 registration operation/claim in the same transaction as its durable register acknowledgement. Any failed eligibility check rolls back the ciphertext update, operation insertion and proof consumption together. The dispatch trigger requires that actual registered claim, not merely a generic VERIFIED job. `verified_at` must be within the original nonce window; a proof verified too late is rejected. A proof genuinely verified before that boundary may be consumed once after the nonce window inside the unchanged original purpose, as selected by the owning Core v5 contract. No new deadline is minted. `native_verified` is a separate narrow proof receipt; `registered` means only the actual durable token-registration acknowledgement. Neither is provider/device acceptance. The later assertion qualification exercises the actual positive writer; all enrolled keys and policy records remain explicitly synthetic fixture authority, and the earlier isolated SQL guard tests also seed their verification receipts.

`private-intake.ts` implements the selected server-only three-header prebody sequence: capture one request window, resolve the actual existing djci principal, check its exact operator-authorization ownership, reserve the original mutation intent, then decode the bounded body and require exact header/body/method/route agreement. These headers never come from Apple paired device headers. Request correlation uses a separate private API domain and literal route. Status and terminal withdrawal do not allocate new positive authority or require a fresh live authorization lease. A duplicate request cannot borrow the winning claim, run another action, or close the original winner's intent. The body budget is ten seconds from original capture and the whole callback budget remains 30 seconds. The intake returns a typed bound context; it does not itself perform a native proof, issue a Source181 capability, or publish a positive native/registration ACK.

Independent whole-source review of 7b8c found a real issuer CAS defect: the original finish method did not compare its winning private claim. Two actual D1 counterexamples were recorded before the fix and both failed. The corrected finish requires the original private claim, exact request hash and original install-record principal; a positive finish additionally joins current authorization/principal state and original expiry. A concurrent loser or cold status reader cannot promote another reservation. Negative own-claim closure remains possible after principal retirement, without creating positive authority. Earlier failing reports and source snapshots are retained outside the source tree; they are not counted as passing qualification.

## Saved-key assertion and Source181 backend

`native-assertion.ts` reads the actual retained job and enrolled public key from D1; its API accepts no caller public key or boolean verdict. It supports a named strict Apple assertion-properties profile with an explicitly stored app identifier and build version, without importing the old rendezvous fixed-QA APP/build/AAGUID policy. The stored native SDK identifier must match SHA256 of the actual P-256 public point. The original frozen transcript, RP-ID hash, signed properties, strictly parsed DER signature and monotonically advancing counter are verified with the actual WebCrypto/PKIJS/CBOR implementations. Unexpected fixed WebCrypto import/digest/verify failures preserve their original cause.

Only the unforgeable in-process crypto receipt can enter the positive counter writer. One atomic D1 batch compares the original native claim, actual key/counter/public-key/policy snapshot, current operator/install state and original expiry; records a unique private commit claim and proof receipt; and marks the original job VERIFIED. JSON cannot manufacture a positive receipt, and a second key-counter contender cannot borrow another commit's ACK. Core's public challenge UUID is mapped to a separate API-generated private job UUID; the latter never enters the transcript or any reply.

`source-backend.ts` implements Source181's original-purpose and native-registration ports using actual stored operator/issuer/principal/native records, actual configuration binding and original request window. It checks the actual signed-environment receipt reference, explicit APNs team/topic/environment, exact original native token bytes and actual verified job. Registration and dispatch remain protected by the independent atomic SQL triggers. The provider is lazy; issue/register/status/withdraw do not require performing APNs transport. Source181's original implementation is unchanged.

These checks do **not** create a genuine native enrollment. The new first-attestation source requires an explicit custodian policy and genuine Apple evidence; it never falls back to an old fixed-QA journal. Actual signed host artifacts, trusted enrollment/deployment-policy production and qualified original cross-domain clocks are still missing inputs. All positive native key/policy/authority records in the local crypto/SQL tests are labelled synthetic; no native SDK, actual key custody, provider or device was exercised.

## Owning private reply port

`server-reply.ts` and `qualification/private-server-reply-vectors.json` fix the six private Core-to-API reply contracts. Common metadata binds the exact private request hash and retained original generation/revision/deadlines. Only the winning `issuer/issue` reply carries a one-time capability; all status replies explicitly lack recovery. Native verification and token registration are distinct states. Unknown keys, cross-route states, substituted hashes, retained-proof-kind changes and secret fields in history replies are rejected. Initial registration mode is `single_original_no_rotation`: a changed token/revision is unsupported and terminally withdraws the existing push child; it cannot remint a purpose, UUID or eight-hour lease. The standalone Source181 rotation capability is not claimed by this receiver increment.

The private HTTP and target transport composition is described below; genuine native enrollment acceptance and production composition remain open. Neither the private reply codec nor a synthetically seeded enrollment is an admitted public receiving factory.

`authorization-resolve.ts` is the private readonly discovery port for an existing operator role. Its exact request scope includes the actual paired/owner/device/source bindings and native target/key; selected-origin and identity/deployment-policy hashes are returned from that one existing role as immutable metadata, never supplied by the caller. Core must bind those hashes to the same retained original child, and cannot initialize a parent or cold restore from the reply. The lookup authenticates the existing djci principal and requires exactly one matching current operator/native policy. It never chooses the latest grant, imports configuration, creates/rotates a token or key, returns a capability/private purpose/job/proof/transcript, or initializes a Core parent. It performs no semantic intent write. Zero or multiple matching grants remain unavailable. Existing grant bounds are returned unchanged as metadata, not a fresh eight-hour window. Lookup selects attestation for one actual unclaimed pending policy, or assertion for the same current enrolled key. This creates neither policy nor enrollment.

The frozen private port packet includes `qualification/private-receiving-ports.schema.json` and independent Python-generated six-route plus resolve vectors. The JSON Schema describes structural envelope DATA (`method`, literal `path`, `direction`, `body`; actual HTTP remains body-only). Runtime codecs additionally enforce retained original equality, request correlation, canonical base64/transcript and original cross-field deadlines. That seven-port schema excludes the separately specified target transport and operator native-policy ports; a source pin is not whole-service admission.

## Private HTTP receiving composition (source candidate)

`service.ts` now composes the six issuer/native endpoints, readonly role resolve, and the four actual HMAC-only operator endpoints. The whole request uses its mandatory original pre-await clock/cancellation window; the operator body budget is ten seconds from capture before authenticating its exact raw bytes. It never bootstraps or rotates a djci token. Only a winning original issuer claim receives Source181's one-time capability. The native challenge reply contains the unchanged canonical R31 transcript; complete selects the saved job kind and reaches the actual attestation or saved-key assertion verifier and atomic proof/key/counter writer. Status never recovers a capability or turns verification into token registration.

`guard-schema.ts` checks the code-pinned actual SQLite view and six trigger definitions before positive receiving work. It does not install schema. `issuer-guard.sql` closes the actual Source181 INSERT boundary against concurrent operator/child withdrawal and original expiry; the separate registration and dispatch triggers retain their earlier atomic proof-consumption and current-key requirements. Qualification includes an explicit absent-issuer-guard control where delayed insertion succeeds, followed by the real guarded rejection after the same negative closure. This control is local synthetic qualification, not an admitted production purpose.

A child can be negatively closed before its issuer exists: `host_wake_child_withdrawals` retains a bounded permanent no-reopen fence, checked before later positive intents/issuer insertion. When no original tuple exists, the HTTP reply remains `history_unknown` rather than inventing original metadata. At fence capacity, an unknown child receives unavailable, while an existing child can still close through its preallocated issuer row. Issuer withdrawal requires its actual selected principal/role but no lost capability, fresh positive native policy, encryption key or APNs provider configuration. It closes only the push child, never its Core display parent.

The current handler implements the private target transport described below, with the first-attestation source described below. Its qualification exercises actual Source181 registration and atomic proof consumption through private HTTP; no public handler is activated. No production migration, Worker import, source publication, deployment, native SDK call or provider request is performed by this increment.

Independent Core review also found a semantic issuer-reply join missing from the private DATA codec: a correct request hash and an answer matching a retained original did not establish that the **sent** issuer original was that same retained original. Three actual API counterexamples (changed owner, source or token digest with its correctly recomputed request hash) failed before the fix. `decodePrivateReply` now requires canonical decoded `input.original` equality with the retained original before accepting an issued ACK. The same three cases pass in the complete 240-case local workerd qualification; earlier schema-reference and runtime counterproof reports remain retained separately.

## Private Source181 target transport

`target-transport.ts` implements `/register`, `/wake`, `/status` and `/revoke` on the existing private prefix. Source181 request bodies and success response bodies remain unchanged. Existing djci stays in Authorization; the issued one-time capability travels in a separate strictly single `X-DJConnect-Host-Wake-Capability` header. The actual principal, three private scope headers, issuer/private-purpose mapping and capability are checked before the body. Register/wake also require `X-DJConnect-Host-Wake-Operation-ID`; it reserves the original per-event intent before the body and must equal decoded `operation_id`. A failed, lost or consumed request cannot retry that same intent or consume another native proof. A different event identity is not an automatic recovery path; Core's owning once-journal must preserve its own UNKNOWN fence.

Every success has the mandatory single `X-DJConnect-Host-Wake-Request-SHA256` correlation header over canonical `["DJC-HOST-WAKE-API-REQUEST-V1","POST",literalPrivatePath,closedSource181Body]`. Core must check it against its actual original request and independently retain parent/currentness/once authority. It is DATA, not permission. Status/revoke do not allocate a positive intent. Revoke closes only the retained issuer child and clears its ciphertext without native-positive/encryption/provider configuration, including at full early-negative-fence capacity. Capless issuer withdrawal remains a separate endpoint. A terminal Source181 `state` of withdrawn/expired always takes precedence over historical `operation_state=registered`; neither status nor a header repairs Core's lost-response fence.

The receiving factory creates a fresh Source181 binding for one delegated callback. Its first Source181 clock read returns the SAME original outer pre-await capture, followed by actual mandatory current-clock reads. Consequently the durable wake's accepted/expiry timestamps retain the original callback boundary rather than restarting 30 seconds after private auth/body awaits. A causal test against the exact former backend fails; the identical test passes with the corrected binding. The unchanged Source181 implementation itself is not edited.

`qualification/private-target-ports-vectors.json` and the matching structural schema cover unchanged bodies, closed source success replies (including minimal 202 UNKNOWN), fixed private errors and header correlation. The reproducible Python generator and actual standard schema checker are included. All provider keys and enrollment/policy rows in qualification are explicitly synthetic; the one simulated APNs response and cancellation controls reach real local crypto/SQL/HTTP code through a software fetch stub, never Apple's network or a device. The original target-transport suite has 263 passes, with no failure or skip; standard schema validation separately has 18 positive and 84 negative passes. Preliminary TypeScript fixture errors and the actual old-clock counterproof are retained as failures, not relabelled passes.


## First-attestation source and immutable proof selection

`native-policy.ts` defines the two closed HMAC-only native-policy create/withdraw contracts. `native-policy-store.ts` retains the explicit original policy, current operator/install binding, target, seven original context hashes, actual SDK key identifier, private custodian key reference, signed host/environment receipt references, App Identifier, bundle version, explicit Apple signed launch category and App Attest environment. The selected iOS/iPadOS profile permits only categories 2, 3, 4 or 5, encoded as four little-endian bytes in canonical standard base64. It has no fixed QA app/build/environment/category defaults. App Attest and APNs environments are separate fields. The pending row is not an enrolled key or permission. Withdrawal disables the associated key and push children without a positive lease, capacity allocation or provider credentials.

`native-state.ts` chooses from actual current policy/key state. The issuer saves that proof kind at its original reservation. A concurrent enrollment cannot turn another already-prepared attestation into an assertion. A pending policy has exactly one original private attestation job; UNKNOWN, rejection or a lost callback cannot allocate a replacement UUID to repair that key. After genuine enrollment, future independently authorized original children may use assertions, while the initial child retains its own attestation job and counter-zero receipt. Legacy unbound QA/v1 key rows are not receiving authority.

`native-apple-evidence.mjs` performs actual CBOR, certificate-path, COSE/public-key, credential identity, RP-ID, nonce, signed-properties and CMS receipt cryptography with code-pinned public Apple roots. The app/build/environment/category come from the retained custodian policy, not caller proof fields. Fixed receipt CRL/OCSP endpoints are bounded by the original native/callback lifetime and response-size ceiling; absent or unavailable receipt status cannot produce a verified result. The carrierless App Attest path claim is protocol/path/validity/nonce qualification, not an invented revocation result. Unexpected failures in fixed trusted WebCrypto preserve their original cause. The pure cryptographic result is not enrollment authority.

`native-attestation.ts` rereads the saved private VERIFYING claim, original transcript/nonce, current operator and pending policy. Its opaque process-local receipt is required by the atomic writer. That writer joins current rows again, enrolls the exact returned key, encrypts the receipt using the existing configured AES key with distinct bound AAD, records the initial counter-zero proof, and completes only the winning original job. The three additional native SQL guards reject competing jobs, late key insertion and substituted initial proof rows; a failed batch rolls back the entire enrollment. No caller SPKI, JWK, positive boolean or JSON crypto receipt is admitted. Schema files are source only and are not installed by this factory.

The public R31 transcript and Source181 body/implementation remain unchanged. Actual SDK `attestKey` and `generateAssertion` selection must follow the retained API-issued kind; local key existence is insufficient. Both use SHA256 of the original raw R31 signing bytes as clientDataHash. The raw opaque SDK proof travels as canonical standard base64, bounded to 9216 decoded bytes. The private API key reference never enters Apple, QR, transcript or public reply. `qualification/private-first-attestation-vectors.json` supplies independently generated protocol shapes and preimages; its positive reply examples are modeled DATA, not genuine Apple proof.

Qualification is deliberately split. The ordinary actual workerd suite passes 299 tests, including real malformed-proof and forged-chain rejection, fixed-root crypto exception propagation, pending-policy HTTP behavior and original target/assertion checks. The separately configured `qualification/enrollment-store.config.mts` passes 11 SQL/coordinator tests using explicitly modeled vendor evidence in an isolated worker process. Those eleven establish transaction, cancellation, counter-zero, competing-writer and immutable-proof-kind behavior only. The same proof-kind race was first recorded RED and then GREEN; the failed run is retained. Standard schema validation separately passes 18 positive and 54 negative first-attestation/policy shapes. Strict TypeScript checking covers both suites.

No genuine positive first App Attest proof, signed iOS host artifact, SDK key creation, real receipt-status request, key custody, qualified cross-domain clock, APNs provider, device, public route, production schema migration, deployment or activation was exercised. Those are outstanding acceptance/effect inputs, not evidence supplied by the synthetic fixtures. This source increment requires independent exact-source review before further delivery.
