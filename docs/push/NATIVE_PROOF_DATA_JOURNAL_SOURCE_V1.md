# Native proof DATA journal: uncomposed source

This increment adds a low-level D1 repository for the existing Core R9/API v2 phase DATA. Every result says `DATA_ONLY_NOT_ADMISSION`. The repository is not a NativeProofPort, does not interpret a passed verification Boolean or invoke a verifier callback, and cannot authorize registration or an SDK/key/token/provider operation. It adds no HTTP route, root import, default factory, deployment configuration, dependency, production migration or runtime schema creation. The schema under `qualification/surface-push/` is a disposable test fixture only.

The four original DATA stages are `prepare_key`, `verify_key`, `prepare_target` and `verify_target`. The original context, data-epoch, bootstrap binding, key-scope, operation and nonce hashes and both fixed deadlines are captured once. Preparing reserves a unique `(job,stage)` claim; verification also spends the original key/target nonce. Separate globally unique operation and nonce tables prevent cross-job and cross-role aliases. A new UUID cannot repair an unknown original operation. Phase words describe stored DATA, never an owner/native verdict or a Core credential.

`reserveDataStage` issues an opaque, frozen, instance-local RAM object only after the actual reservation transaction returns. Its private WeakMap entry is consumed synchronously before completion input validation, cancellation checks or any await. Cloning it, constructing another repository or reading database rows cannot recreate it. No public status, reply cache or reissue operation exists. On lost replies the original claim remains unavailable; an independent exact original-job retirement is possible, not a reset/retry with a replacement operation.

Completion uses SQL predicates that jointly bind original job phase/revision/context/epoch and the reserved claim. A global key-ref counter row also binds the immutable key-scope, expected counter revision and a strictly increasing unsigned-32 counter. Fresh-key DATA inserts counter zero only if that actual key-ref hash has never existed. Existing keys share that counter across jobs and management data epochs; a different job, principal epoch or key-scope cannot recreate/reset it. Actual attested key identity and the genuine scope binding are still future verifier/admission responsibilities; accepting hashes here does not establish them.

A lost counter CAS is not an SQL exception. If it updates zero rows, job/claim/transcript updates also update zero rows. Conversely, a lost job CAS cannot leave a counter advance. Transaction-local claim markers and a `CHECK(valid=1)` invariant abort any partial marker set inside SQL; they are inserted/deleted in the same batch. The implementation never inspects row counts after an await and calls that a rollback. Actual trigger controls demonstrate that even a job revision changed after a counter update causes the whole transaction, including that trigger update, to roll back. The final DATA read is part of the definitive transaction through a captured `first-primary` D1 session.

`close()` is irreversible. A real AbortSignal, local exact-job retirement or close is checked before submission, after every awaited batch and immediately before returning a reservation/result. Local retirement conservatively poisons the exact `(job,context)` for that instance before submission, including an unknown retirement result; no local poison is cleared to enable retry. Another repository's retirement is enforced by the SQL predicates when ordered before the transaction. A retirement in a different instance after the transaction's snapshot is not instantaneous globally observed currentness: the returned value is only a committed DATA fact, never present authority. A future real proof-port must retain independent original owner/clock/lifecycle witnesses and final publication guards.

A submitted database operation may commit despite cancellation, closure, retirement or a lost reply. In that case the DATA result is suppressed when the condition is locally observed, while the actual committed counter/job/nonce truth remains. Terminal retirement never undoes a counter and targets only the exact original job/context/epoch, not the latest job for a device. SQL statement failures separately roll back their actual batch. Unexpected D1 exceptions are rethrown unchanged; they are not native proof rejection.

The repository has no wall/monotonic clock provider. Deadline numbers are immutable DATA with safe-integer bounds, not a claim that they are currently valid. `data_epoch_sha256` is equality DATA, not a genuine boot or owner witness. Genuine integration must reject missing actual operator/Core owner admission, qualified original clock mapping, native verifier/policy and accepted persistence provider **before invoking these mutations**, and keep original witnesses across all subsequent awaits. [D1 batch/session semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/) and [Sessions consistency](https://developers.cloudflare.com/d1/best-practices/read-replication/) support the SQL/process tests; they do not prove physical power-loss durability, restore/backup rollback protection or durable-before-SDK effects in an unselected deployed provider.

Actual disposable Worker/D1 controls cover four-phase progression, two-adapter reservation races, global counter races, both zero-row CAS losses, global scope/epoch reuse, SQL invariant/statement rollback, once consumption before validation, lost reservation/completion replies, postcommit local close/cancel/retirement, exact original-job retirement, immutable deadlines, closed input snapshots and numeric bounds. The dedicated pinned read-only workflow typechecks source and tests; the existing Validate workflow runs the actual Worker tests. The initial 55-case focused PASS predates the extra locally observed retirement control; it is retained separately from the final source qualification. The initial dedicated typecheck's four `unknown` test-snapshot diagnostics were repaired before the first Worker run and are not counted as PASS.
