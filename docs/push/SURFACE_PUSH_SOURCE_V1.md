# Typed surface push: source component and Core wire candidate

This is the API-owned source component for Peter's selected WidgetKit/ActivityKit registration increment. It is not a released cross-repository contract, public endpoint, provider/native test or installed feature. Base protected main9ab24315a10b569b84e738d09bf32df6da12e38b and the separate frozen maintenance PR131 are preserved. No source from Core or Apple is written here.

The existing public Worker **does not import or route this component**. Candidate paths below run through `createSurfacePushHandler` in isolated local workerd/D1 tests. Public root routing, purpose-scoped capability issuance, the real provider-JWT adapter and exact Apple content-profile admission are separate required integration decisions before protected operational delivery. No deployment/configuration/key/token or real notification is performed by this source work. The component supports no self-service capability minting. Migration0009 creates empty tables only.

## Core join: closed version1, not generic app-push fallback

Candidate server-to-server POST paths: `/v1/push/surface/register`, `/revoke`, `/event`, `/status`. Every body has exactly `contract_version:1`, `registration_id`, opaque string `generation`, integer `revision>=1`, canonical UUIDv7 `operation_id`, and opaque64-lowercase-hex `binding_id`, `device_binding`, `owner_binding`. Core derives the bindings from its authenticated owner/install/device/Session/grant/source context; clients cannot self-assert them. Requests to this component accept no Origin, cookies, query/fragment, encoded body, unknown/duplicate JSON keys, non-UTF8 or body over16KiB. Content-Type is exactly application/json.

Register adds `expires_at_ms`, `token_role`, `platform`, `apns_environment`, `target`, `apns_token`. It matches Core's supplied WIP `SurfacePushRegistry` body. Token is lowercase even-length hex32..4096characters, a bounded application policy matching the Core candidate, not a fixed Apple token-length claim. Expiry must be future and at most8hours at first admission, within the capability's deadline. Rotation retains the exact original expiry and target metadata. There is no renewal-on-retry/read/push.

Roles are `widget`, `live_activity_update`, `live_activity_start`. Every target has `instance_id`, `app_bundle_id`. Widget adds exactly `extension_bundle_id`, `widget_kind`; update adds `activity_id`, `attributes_type`; start adds `attributes_type` and no existing Activity ID. Parent app bundle, role, platform, environment and native extension/kind or attributes type must exactly match server-owned capability configuration. Topic is never a caller field.

Revoke and status use only the common coordinates/bindings. Revoke must include contract_version1; the initially observed Core revoke body still omitted it. Status is an API read-only addition needed to reconcile an unknown relay outcome without a new write, retransmission or lease. Core's RAM registry alone is not proof of a relay result after loss/restart.

Event adds `event`. Widget allows only `widget_reload` with no content/profile/payload. Activity update/end/start candidates add `profile_id` and `payload`; no real activity profile is admitted here. Profile selection is an explicit compiled server adapter, never an environment/request-supplied schema. Start dispatch is unconditionally denied. Registration of a start token does not start, update or end an Activity and cannot substitute for an update token.

## Narrow server principal and token storage

This component accepts only a distinct Core-only purpose bearer `djcs_…`, hashed in `surface_push_capabilities`; ordinary `djci_` app/install credentials and extension background-read credentials are refused. Provisioning is not implemented or performed here: it requires an explicit issuer/lifecycle join with Core before root admission. Each capability binds one install, paired device hash, owner hash, role, platform, configured parent/extension metadata, environment and absolute expiry. It has finite non-revoke/revoke operation budgets and a separate once-event budget. Successful non-revoke traffic cannot consume the reserved revoke budget. Capability metadata is immutable except revocation; policy/subject changes require revoke and a fresh capability.

Core retains request-local current owner/Session/grant/source authority and the separately bounded background-read credential. The relay validates the authenticated capability and exact opaque bindings; it cannot infer current HA authority from client JSON or an APNs token. No app/HA/Profile/Session bearer or APNs provider key goes into the extension/app group or this new registration wire. Apple pending-token capture is not server registration or content permission.

Raw native token is transient. Targets store AES-256-GCM ciphertext/nonce, authenticated with target/capability identity, generation/revision, original expiry, canonical target metadata, role, parent bundle and environment. Revocation clears token ciphertext/nonce while keeping the durable fence. No raw request/token/provider endpoint is persisted in the operation ledger or emitted in responses/diagnostics. Key-version rotation/provisioning and physical retention/cleanup require separate reviewed operations; no fallback to plaintext or other keys is attempted.

## CAS, early revoke and exact acknowledgments

First registration is revision1. Rotation requires next revision in the same opaque generation and immutable target/bindings/expiry. The identity includes registration ID, generation and Core binding hashes under the capability. A request cannot overwrite another generation/owner/device/Session binding or ordinary app-token row.

A revoke arriving before its register durably inserts a token-free tombstone, even with no target yet. That generation is terminal; delayed registration/rotation cannot resurrect it. A stale revoke revision cannot invalidate a newer accepted rotation. A new explicit Core grant generation is a different identity; an old generation's tombstone does not revoke it. Core also withdraws its local read authority before awaiting the relay and rejects late acknowledgments against its own newer/tombstoned state.

Responses bind `contract_version`, `success`, `registration_id`, opaque `generation`, `revision`, `operation_id`, `expires_at_ms`, `state`, `operation_state`, `current_revision`, `provider_status`, `replayed`. Register success is true only for the exact still-current accepted revision and original expiry. Revoke success requires its exact tombstoned revision and state revoked. A historical accepted register does not return current success after revoke or rotation. An unseen early revoke has no authoritative original expiry yet and returns0; revoke acknowledgment never grants a lease. These extra fields do not replace Core's exact typed checks.

UUIDv7 operations have their original five-minute execution window and30-second future skew, matching Core's OperationJournal. Canonical request digest plus capability/operation ID are durable. Same operation/same input returns its stored outcome/current state; conflicting ID reuse fails. An earlier CAS conflict never becomes successful when later state changes. Status does no write and can read historical outcomes under still-valid authentication. Its registration ID, generation and revision must match the stored operation exactly; a request combining an old operation ID with a newer revision returns409. An exact historical status returns its original coordinates with success false when a later rotation is current. Tombstones are not automatically pruned; cleanup must not reopen an unexpired operation or generation.

## One provider attempt, not exactly-once delivery

A real SQLite transaction reserves the event and a durable dispatch marker precedes the one outbound attempt. Duplicate requests and handler restart cannot retransmit a reserved/unknown event. Revoke/capability/expiry are rechecked before dispatch. A change after an already-authorized attempt starts cannot retract APNs traffic. A lost response remains unknown and never authorizes an automatic new attempt.

Widget headers use `widgets` and `<configured parent>.push-type.widgets`; body is only `{"aps":{"content-changed":true}}`. Live update/end uses `liveactivity` and `<parent>.push-type.liveactivity`. A separately admitted compiled closed ContentState parser and external transport right are mandatory. It preserves the original observation and content deadline (at most120seconds here), supplies timestamp/stale-date, and end includes final content and an immediate dismissal date. The original content deadline is rechecked after provider authorization and before dispatch; APNs expiration and the remaining request timeout are capped by that deadline. Expiry during authorization is durably not_sent with no retransmission. The request builder also rechecks expiry after the durable dispatch marker. Expiry there prevents the provider call and conservatively leaves an unknown outcome. Start remains denied. Current tests use only a clearly synthetic profile; no real Apple ContentState/attributes/export authorization is invented.

The provider adapter is absent by default. No headers/host/topic/URL are caller-selectable, no alert fallback or broadcast is implemented, and no environment retry occurs. Provider200 means accepted by APNs, not delivered/rendered/user accepted. A delayed410/BadDeviceToken invalidates only the exact revision sent. Unexpected transport outcome stays unknown. Local tests inject transport; no provider JWT/key is generated or read and no APNs request is sent.

## Platform and remaining integration gates

WidgetPushHandler DocData lists iOS/iPadOS/Mac Catalyst/macOS/watchOS/visionOS26.0+. tvOS is absent. ActivityKit native tokens originate on supported iOS/iPadOS; mirrored Watch/Mac surfaces are not extra token destinations. Core checks OS availability before forwarding; capability provisioning must bind a genuinely supported signed target. No all-platform native acceptance follows from these enum values.

Before root/producer admission: Core must adopt this exact wire/version, status and acknowledgment semantics and narrow credential scope; Apple/Core must supply closed activity schemas/date encoding, explicit external-content/presentation rights and widget background-read/credential lifecycle. The real provider adapter, capability issuer/revoke path, finite retention/cleanup, abuse/cost admission and root provenance must be reviewed together. New source tests and local migration do not close those gates. Original rendezvousA/QA/native holds and all22 full-service gates remain unchanged. Human release/install/deploy holds remain in force.
