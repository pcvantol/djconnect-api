# Automatic native push enrollment proposal

The HA-dev MVP has one user flow: pair DJConnect with HA-dev, turn on the desired channel in the app, publish a real update, and see it on the selected device. The paired Apple app user opts in separately for each device and channel. The HA installer has no action to take, and the user does not enter an installation token or ask an operator for approval. Fresh registrations receive a new API principal and cannot adopt prior grants. Recovery and takeover are outside MVP implementation and acceptance.

## Trust and scope

The normal HA app pairing currently obtains a per-installation `djci_` bearer via `POST /v1/pairing/bootstrap-proof` and `POST /v1/install/token`. The legacy bootstrap route validates request fields and rate limits issuance. It does not verify a signature over the original authorized pairing. A bearer from that path and proof of possession of a new Core key cannot establish the first trusted key for an installation.

For a fresh principal, verify the attested DJConnect host app, the current original pairing captured by that app and Core, and the exact channel opt-in. The person who installed HA is outside this flow. The API assigns a fresh identity and binds it to the exact installation credential and proof. The legacy HA ID is only a correlation value.

Push defaults to off. One consent coordinate is installation, owner, physical device, pairing generation, channel and consent generation. Target digest, role, public purpose key thumbprint and original deadline are also bound. A different device, role or pairing needs its own consent. The Core signer must represent the actual explicit user action under the current native pairing. Local display, retained content, an OS notification permission, shared settings and pairing alone cannot authorize push. Separate Apple proof binds the exact target where required.

## Original pairing witness for first trust

The existing HA `POST /api/djconnect/v1/pair` response returns the local paired bearer, installation/device metadata and optional setup state. The pending config-flow branch can return success with `setup_pending: true`. Apple saves the returned bearer on pairing success. Its later authenticated status check can confirm that HA still accepts that bearer. Neither response binds an API challenge, Core public key or verifiable durable pairing generation. Core's private pair journal already records a durable auth generation and retirement. Its local acknowledgement is a useful currentness input and stays private.

Add a separate authenticated HA message, proposed `POST /api/djconnect/v1/push/native/pair-witness/challenge`, after pairing is durably committed and still current. Use the ordinary paired bearer only on that HA connection. Core requests the existing proposed central `/v1/push/native/key/challenge` with its installation credential and Core public key thumbprint. The HA message returns the original challenge and a closed transcript for the paired Apple host. It must derive pairing, owner and device bindings from the current authenticated durable record. The client cannot select those values from request data.

The proposed `djc-native-pair-witness/1` transcript binds `api_audience`, `challenge_id`, `challenge_nonce`, `expires_at_ms`, `api_installation_id`, `install_credential_id`, `pairing_generation`, `pair_binding`, `owner_binding`, `device_binding`, `core_key_thumbprint` and `operation_id`. It contains opaque bindings and no raw pair code, HA bearer or APNs token. The Apple host uses its genuine App Attest proof over a domain-separated digest of those exact canonical bytes. It only signs a transcript from the same authenticated HA origin and original pairing attempt, after confirming setup is complete. Core submits the same transcript and Apple proof along with its own challenge-bound proof of possession to central `/v1/push/native/key/register`.

App Attest authenticates the host app and its binding to the transcript. It does not independently certify a self-hosted HA installation ID. If the central service has no prior trust for the HA installation, the new principal must use an API-assigned immutable installation identity bound to the exact attested credential. The legacy caller-supplied `ha_install_id` is a compatibility coordinate. To adopt or recover a preexisting API principal, require an independently verified link to that principal, such as a current trusted Core key or a selected pairing authority for that installation. A legacy bearer plus a newly attested app cannot replace a preexisting principal. Core reviewed the fresh-principal namespace. Its private pair and profile identifiers remain in HA. Core derives domain-separated opaque pairing, owner and device bindings from the original current record. Exact derivation and platform evidence must be agreed before mounting the routes.

The API stores the challenge, exact credential, pending operation, captured key and original deadline. It rechecks them at commit, consumes the challenge once, and atomically registers the first key or returns a conflict. Lost response uses exact status with proof of the same key. An expired or retired pairing never restarts from status. A lost or retired key requires explicit recovery against the current independently authorized pairing, a fresh nonce and a new key revision. Retire the previous revision and dependent grants, retain the tombstones, and require new explicit consent when the pairing or relevant device/channel binding changes.

### First-key fixture for WidgetKit HA-dev

The proposed shared fixture is [first-key-witness-vector.json](../../qualification/native-push-mvp/first-key-witness-vector.json). Its challenge request supplies the Core operation ID, opaque pairing generation, pair, owner and device commitments, and SHA-256 of the Core P-256 public key in DER SPKI form. Core captures the original durable, still-current PairJournal acknowledgement and the separate current server-managed device-to-Profile mapping. Both inputs and their private identifiers stay in Core. The fixture uses synthetic commitment outputs.

The original PairJournal acknowledgement contains the instance and authentication generation. Resolve the owner through Core's server-managed device binding without client hints or fallback. Capture the mapping's non-reusable revision with the original acknowledgement and bind it into the opaque `owner_binding`. Recheck both originals before requesting a challenge, forwarding a proof or accepting a registration or status receipt. Reassigning a device from A to B and back to A must invalidate the old capture even if the pairing object, credential and final Profile ID match again. The integration test should change only that server mapping during a pending operation and show that both a direct change and an A-to-B-to-A change reject the original operation. This condition still needs live Core storage and transport evidence.

For this WidgetKit candidate, the API compares opaque values only within the exact pairing, from the saved first-key operation through status and the device/channel grant. Core may derive them with a separate local 32-byte HMAC-SHA-256 key, distinct versioned domains and compact JSON arrays bound to the original PairJournal store instance and authentication generation. Bind the server-resolved Profile and private device binding generation in the owner domain, and the server-resolved device ID and client type in the device domain. Encode the commitments as lowercase SHA-256 hex. A Profile shared by two pairings has two unrelated owner commitments. For an owner-wide action, Core resolves its affected pairings locally and authorizes each exact scope. A restored copy without the original current authority cannot reconstruct permission.

The challenge response supplies the central installation and credential IDs, original nonce and deadline, and expected revision zero. API derives the credential ID from the authenticated installation bearer and reserves the installation ID itself. The API saves the request fields alongside that response and reconstructs the register transcript from the saved reservation. The register envelope echoes those fields and supplies the SPKI, Core signature, and genuine Apple proof with its key identifier and proof kind. An envelope mismatch rejects the request before proof verification. The fixture supplies a software Core signature and the exact Apple digest.

The canonical statement is a compact UTF-8 JSON array with the field order in [first-key-wire.ts](../../src/native-push/first-key-wire.ts). The domain includes the HA-dev audience, HTTP method, register route and WidgetKit first-key purpose. Core signs the exact bytes using P-256 ECDSA with SHA-256 and sends the fixed-width 64-byte signature as unpadded base64url. Apple passes the raw 32-byte SHA-256 of those same bytes to App Attest as `clientDataHash`. The API calculates that digest itself. The first live trial requires a fresh App Attest attestation on the selected signed HA-dev app against this exact saved transcript. The live proof must be coupled to current original PairJournal authority and the same active installation credential at commit.

Core persists the original operation, reservation, transcript digest and signing-key reference before submitting. API commits the first key and the immutable receipt together with challenge consumption. Core checks the returned operation, both API IDs, pairing generation, key thumbprint, transcript digest and original deadline against its saved operation before storing the API-assigned registry generation and revision one.

If the response is lost, the proposed `key/status` flow authenticates the same active installation credential and asks the same Core key to sign a fresh API nonce in the distinct status domain. The signed request must bind the exact original operation, installation and credential IDs, transcript digest and original deadline. Limit the status nonce to the original window. Return the existing receipt only if the original committed row, key revision and pairing authority are still current. Repeated authorized reads return the identical durable receipt. Missing, expired, retired and mismatched outcomes stay closed and cannot reserve a replacement or extend a deadline.

The [status fixture](../../qualification/native-push-mvp/first-key-status-vector.json) uses one synthetic key for its own registration and readback signatures. Core requests the nonce via `POST /v1/push/native/key/status/challenge`, presenting the same installation credential and the persisted operation ID, API installation ID and transcript digest. API resolves the credential ID from authentication and constructs `statusChallenge` from the original committed row and its own one-use nonce. Core compares the returned original fields to its persisted operation before signing. It posts the exact returned fields and `core_signature_b64url` to `POST /v1/push/native/key/status`. API verifies against the stored public key, checks the current registration and pairing authority, and consumes the status nonce before returning the stored receipt. A repeated authorized read uses a new nonce for that same receipt. Core uses a fixed, explicitly selected HA-dev HTTPS origin and disables redirects and automatic retries on these requests. Both sides bound status attempts by the original deadline.

The receipt records key registration. Outstanding grants, existing registrations and delivery rights must be checked separately against their own device, channel, target and consent authority. This fixture provides neither adoption of prior grants nor an enrollment or send operation.

### First live candidate boundary

The separate WidgetKit Worker and its isolated database and version checks form the deployment boundary. Its four first-key handlers use the [isolated D1 schema](../../qualification/widget-ha-dev/first-key.sql). The default Worker has no selected first-key policy and returns HTTP 503 before reading the body or looking up a credential. The local qualification supplies a synthetic policy through server composition and exercises the real Worker and D1. The ordinary installation bearer is required. API derives the credential ID server-side and checks the active ID and token hash in each D1 write.

The local wire uses strict JSON objects with the following exact keys. All four requests are POST to the exact isolated HTTPS origin, with `Content-Type: application/json` and an installation bearer. Success is HTTP 200 with a no-store response. First-key routes use an `error` field on failure.

The maximum size of the complete UTF-8 JSON body, including whitespace, is 32,768 bytes for `register` and 16,384 bytes for each other route. A 16,384-byte decoded proof occupies 21,848 bytes in standard base64 before the rest of the JSON is added. A body over its route limit returns HTTP 413 with `payload_too_large`.

| Route under `/v1/push/native/key/` | Request | Response |
| --- | --- | --- |
| `challenge` | The exact `challengeRequest` object in the first-key fixture | The fixture's `challengeResponse` shape. API caps the original expiry at 120 seconds and the server policy's deadline. An exact replay before expiry and registration returns the original reservation. |
| `register` | The fixture's `register` object plus required `apple_proof`. That object has exactly `kind` (`attestation`), `key_id_b64` (32 decoded bytes) and `proof_b64` (1 through 16,384 decoded bytes), both canonical standard base64. | The exact `committedReceipt` shape. One atomic write consumes the challenge and stores the key and immutable receipt. |
| `status/challenge` | `contract_version`, `operation_id`, `api_installation_id`, `transcript_sha256` | The exact `statusChallenge` object in the status fixture. There is at most one outstanding status nonce per operation. Its lifetime is at most 15 seconds within the original window. |
| `status` | The exact `statusChallenge` object plus `core_signature_b64url` | The same stored `committedReceipt`. A valid read consumes the nonce in the database. |

Missing or malformed bearer returns 401, as does an inactive bearer when looked up. With a selected policy and a syntactically valid bearer, `register` checks the request shape and proof kind before any database lookup or verification. It returns HTTP 403 with `widget_first_key_proof_rejected` for `kind: "assertion"`. Rejected proof or pairing authority also returns 403. A stale, mismatched or already consumed operation returns 409. An absent, unavailable or retired server policy returns 503. No response contains a push grant, token or send authority.

Assertion support requires a different verifier contract. Verification must be read-only and return the verified Apple key identity, public key revision and environment, the exact saved transcript and policy binding, the expected stored counter and the verified higher counter. One database transaction must compare and advance that counter, consume the original challenge, and commit the first key and receipt. It must still enforce current credential, policy, key revision, recorded retirement and the original deadline. A guarded write that matches no row must abort the entire transaction. Concurrent requests cannot both consume the same challenge or expected counter. A failed or aborted transaction consumes neither. If the HTTP response is lost after commit, both changes stand and Core reads the original receipt through the signed status flow. This transaction is required before enabling assertions.

Select one signed iPhone or iPad host artifact for the first run. The server policy binds the exact App ID, platform, build, App Attest environment and launch validation category to the selected signed artifact and original challenge. The [WidgetKit verifier adapter](../../src/native-push/first-key-apple.ts) calls the existing Apple evidence verifier with the original transcript bytes, which that verifier hashes once for App Attest. Its current cryptographic proof limit is 9,216 bytes. The larger wire limit is a transport limit. The adapter needs a selected signed app policy and enforces the original challenge deadline. Existing host-wake policy, prior app keys and registration receipts stay scoped to that service. The historical Rendezvous development build list and VibeCast QA policy are separate.

The API checks Core pairing authority before and after Apple verification. Its database also stores an irreversible marker keyed by the opaque original pairing binding. An authorized server caller can record that marker idempotently, even before a challenge exists. The database refuses new challenges, key commits and status reads once the marker is recorded. Core still needs to supply authenticated currentness and retirement to the API. The storage operation has no public endpoint.

Live deployment requires the exact isolated HTTPS origin, an isolated D1 with the new schema and ordinary HA-dev credential issuance and lookup in that database, and an audited server composition of real App Attest and current Core pairing authority. The signed iPhone artifact must contain the first-key client. The composition must enforce its original deadline, supply a durable retirement signal and apply bounded admission and retention for pending reservations. The checked-in Worker entry selects no policy. Changing only the origin or environment cannot enable the routes.

Core compares the original PairJournal object, owner generation and installation credential with its durable state after receiving the nonce. For register it rechecks after Apple proof returns and signs the saved register transcript immediately before dispatch. For status it rechecks after the fresh status nonce returns and signs that statement immediately before dispatch. The API verifies that operation-bound signature and the corresponding proofs, then atomically compares its current credential, original operation and key or nonce state, deadline and any recorded retirement before committing or returning the stored receipt. Core rechecks the same original authority again before accepting either response.

The API and Core checks are at different points. If a retirement occurs in HA after Core signs and the retirement has yet to reach the API, the signature alone cannot tell the API that the operation has changed. The first runtime qualification must demonstrate this ordering and keep the returned key unusable for push without a separate current grant check. A strict claim that retirement blocks the remote key commit or receipt before its own arrival requires a shared ordering mechanism.

### Proposed HA-dev authority and issuer boundary

Use a dedicated authenticated ingress for Core's outbound requests. One option for the selected HA-dev instance is a Cloudflare Access machine identity with an audience exclusive to this ingress, a pinned identity and an API-managed mapping to the permitted installation credential and generation. Validate the Access assertion at the ingress. Access context does not cross a service binding, so the internal entrypoint receives only the scoped operation the ingress has authorized. A separately provisioned Core signing key or mTLS identity can supply the same machine authentication if its custody and mapping are qualified. The installation bearer identifies the token row and the first Core key proves possession. Both are checked independently of machine authority.

Core resolves the original PairJournal and owner mapping before sending a positive currentness decision. The API checks that decision against the exact saved pairing and the independently authenticated Core identity.

Retirement has a separate purpose. Core sends a stable event ID and the exact original pairing tuple under the trusted machine identity. It stores the event with the local retirement and retries until it receives an authenticated acknowledgement for that binding. The delivery request has fresh authentication on each attempt. The original registration deadline identifies the operation and does not expire the retirement event. The API must resolve the original tuple from authoritative state before calling `retireWidgetFirstKeyPair`, including when the original bearer has since rotated or no first-key reservation exists. Acknowledge only after the idempotent D1 insert completes. The acknowledgement establishes the API fence from that write forward. An unreceived event cannot undo an earlier remote commit.

The [private issuer](../../src/native-push/widget-install-issuer.ts) uses the existing bootstrap and token repositories behind the dedicated ingress. Bind it and `WIDGET_HA_DEV_DB` to the same isolated D1 database with the install-token, bootstrap-proof, rate-limit and first-key tables. The WidgetKit Worker keeps the issuer routes unmounted. The test exercises private bootstrap and exchange on the same D1 binding and confirms the exact credential ID at the first-key challenge.

Both issuer requests use compact canonical JSON with a 4,096-byte limit and separate Core machine authentication. Send `POST /v1/install/bootstrap-proof` with exactly `ha_install_id`, `device_id`, `client_type` (`ios`), `integration` (`djconnect_hacs`) and `integration_version`. The issuer returns `ok: true`, `bootstrap_proof` and `expires_at` in UTC ISO 8601. The proof lasts 60 seconds. Send `POST /v1/install/token` with the same fields plus `bootstrap_proof`. The response preserves the existing install token fields and supplies the API credential ID. The authenticated server mapping must independently match the original installation and device at both steps. Its opaque scope ID must change on authority replacement. The issuer stores that scope ID with the proof and refuses an exchange from another mapping generation. The proof is single-use. If a consumed proof cannot complete exchange, Core must request a new proof. Live Access verification and mapping remain deployment inputs.

#### First-key currentness v1 accepted by Core

Core confirmed the four request shapes and the status test vector against API commit `585af57bb2306d37f17cb6de238c0fb441e46f8b` in its isolated HA-dev source trial.

Core sends the existing first-key request on the private HTTPS ingress, with its ordinary installation bearer and its separate Cloudflare Access machine authentication. The ingress verifies the Access identity and scopes it to the original installation credential and pairing authority before forwarding the authorized operation. There is no separate currentness endpoint. Send the body as compact UTF-8 JSON with sorted keys and no whitespace, BOM or duplicate fields. Keep the existing route size limits.

Send one `X-DJC-First-Key-Currentness` header containing a compact canonical JSON object of at most 2,048 ASCII bytes. A valid object conveys a positive decision only after machine authentication and tuple verification. It has exactly these fields.

| Field | Value |
| --- | --- |
| `contract_version`, `api_audience` | Integer `1` and `djc-native-push-ha-dev/1` |
| `action` | `challenge`, `register`, `status/challenge` or `status`, matching the request path |

For register and both status routes, clip the decision expiry to the original operation deadline. For status reads also clip it to the status nonce deadline. The API claims each decision once in D1 for the exact credential ID. Concurrent reuse returns a conflict. A retry needs a fresh decision for the same original operation. A fresh challenge decision can recover the original reservation within its original deadline. A fresh status decision still needs an unconsumed nonce, and a lost register response is read through the existing status flow. After a claim, a failed or interrupted request can consume the decision without committing a registration. No decision extends either the reservation or a status nonce. Expired claims can be pruned.

The API checks authority and freshness before and after Apple verification. The D1 write checks the decision expiry and the retirement marker. Once retirement reaches D1, an earlier positive Core decision cannot reopen that pairing. Retirement remains an independent event under retire v1. The [synthetic status vector](../../qualification/native-push-mvp/first-key-currentness-vector.json) includes the complete request bytes and canonical header. The local Worker uses injected machine authority for qualification.

#### Minimum trusted publisher for the HA-dev trial

One environment assignment selects a single HA-dev Core runtime, the private origin and D1, the Core Access machine identity and a separate publisher authority. Give the publisher the exclusive server-side write path for the authority tables. The request Worker only reads these tables. The publisher must read the selected runtime's durable pairing, installation and consent records through a trusted server path. A paired app request, installation bearer or first-key payload cannot publish them. This trial covers one selected runtime and one active device mapping. Additional devices need an explicit mapping model.

1. **Ordinary pairing.** Once the real PairView or config-flow handoff durably records the original PairJournal entry, the publisher verifies the same loaded runtime, entry and original auth generation. It derives the installation and device coordinates from that record and allocates an opaque server scope. It writes the machine mapping for the preassigned Access identity. The operator assigns the environment once. The user pairs normally and never receives a service token or manually provisions an installation. Core requests and exchanges the private bootstrap proof, then reads back the exact credential ID from durable local storage. The publisher confirms that ID against the scoped credential in isolated D1. Bootstrap alone supplies no WidgetKit consent.
2. **Opt-in and operation publication.** WidgetKit starts off. After the user opts in on the original device, Core persists the consent generation, resolves the current device-to-Profile binding, and stages the original operation and retirement coordinates. Before any API challenge, the publisher reads back that exact durable capture and the current consent. It writes one row keyed by `scope_id`, `credential_id` and `operation_id`, with the exact pairing generation, pair/owner/device bindings, Core key thumbprint and original retirement request deadline. Keep the consent generation in the authoritative capture and bind the operation permanently to it. The same row carries `current=1` and the immutable historical tuple needed for retirement, even if no challenge is ever issued. An exact retry reads back the same row. A changed tuple or a retired operation cannot overwrite or reactivate it.
3. **Currentness and commit.** Core rechecks the original pairing and consent before each request and after receiving a response. The Worker separately verifies the Access identity, active credential, operation row and fresh request-bound currentness decision. In the dedicated Core Worker, challenge reservation, key commit, status nonce issuance and receipt readback also compare the exact current machine and operation mapping in the D1 statement. The same check guards replay reads of a previously saved challenge or nonce. A first-key receipt establishes only the key registration. Provider access requires a separate grant for the exact device, channel and consent generation.
4. **Opt-out, unlink and provider handoff.** Core closes the local consent generation durably before issuing more currentness decisions and queues its withdrawal. API opt-out closes the matching operation rows and the grant for that WidgetKit generation. An unlink uses retire v1 for the original pairing and keeps its historical rows, including after credential rotation. A fresh opt-in needs a new consent generation and operation. It does not reopen an old operation or retire unrelated channels. Before handing a publication to APNs, the delivery owner must recheck the exact grant, consent generation, publication and durable revocation against one ordering point shared with revocation. A delivery handed off before that point cannot be recalled. When the provider fence or current confirmation is unavailable, provider dispatch stays closed.

Qualification must trace one ordinary fresh pairing through publisher readback, bootstrap and challenge without an operator-created per-installation credential. It must also refuse a caller-supplied or restored pairing and a device owner change followed by a return to the old owner. The isolated D1 test withdraws the operation after the last successful authority check and immediately before the write. It verifies that the Worker neither creates a new challenge nor returns a previously saved challenge. The live trial must still exercise the full consent-to-mapping path, delayed retirement before any challenge, retirement after credential rotation and revocation before provider handoff. The trusted publisher and provider ordering still require implementation and verification. The source candidate stays closed until their provenance is established.

| Path | Body | Durable result |
| --- | --- | --- |
| `/v1/internal/widget-core/bind` | `contract_version=1`, `ha_install_id`, `device_id` | Allocate the server scope for the configured Core machine. Identical retry succeeds. A changed binding or disabled mapping conflicts. |
| `/v1/internal/widget-core/operation` | The exact retire v1 object without `api_audience` and `event_id`, plus positive `consent_revision` | Store the immutable current and historical operation under the issued credential and server scope. The credential must be active and belong to that scope. Identical active retry succeeds. A conflicting or withdrawn revision fails. |
| `/v1/internal/widget-core/withdraw` | `contract_version=1`, `pair_binding`, positive `consent_revision` | Persist a monotonically increasing withdrawal through that revision for the exact WidgetKit pairing in this scope. An older duplicate leaves the greater revision in force. |

A successful response is HTTP 200 with `{"ok":true}` after durable write or matching readback. Withdrawal fences both newly proposed operations and all first-key writes at the withdrawn revision or earlier. It preserves the historical tuple for retire v1. A fresh higher revision needs a new operation ID. The ordinary ingress does not route publisher operations. The [server-only publisher](../../src/native-push/widget-core-publisher.ts) remains unavailable until a separate authority supplies the selected runtime and verifies durable provenance. The isolated test starts with no device row and exercises binding, bootstrap, exchange, operation publication, challenge and withdrawal under synthetic trusted publisher input.

## Fresh WidgetKit acceptance wire

The paired Apple app starts the request after its user explicitly opts in. Core supplies the current durable PairJournal acknowledgement from the original completed pairing after install credential storage. The API challenge is single-use and tied to the exact active installation credential, app key, pairing commitment and widget target. The attested app proves the exact signed opt-in transcript. The API validates the same pairing against the trusted Core input and verifies the platform-specific host proof. A caller-provided pairing ID is insufficient. No legacy grant is imported.

The positive path creates one fresh principal and a grant for that exact device and widget target. The offline wire trial must reject absent opt-in, a proof signed by the wrong app key, cross-pairing or target substitution, consumed or expired challenge, and an installation credential replaced between challenge and commit. Opt-out revokes only the selected widget grant. Unlink retires the pairing and its pending challenges and grants. A late request or retry cannot revive a revoked grant.

The unmounted local Workerd/D1 trial in `qualification/native-push-mvp/widget-wire.ts` exercises the challenge and exact signed target. Its Core capture is a fixture of the original durable pairing. When opt-out or unlink commits before the activation write, that write must refuse even if its final external currentness check returned an earlier positive snapshot. Opt-out covers both pending and active operations for the selected target, while a retired opt-out witness cannot affect a fresh opt-in. It exercises no Apple SDK, provider or HA-dev route. The shared preflight tests cover all four channel identifiers; they do not exercise channel-specific issuance or dispatch.

### Core confirmation at commit and delivery

The local capture can check `isCurrent()` directly. A deployed API must obtain a verifiable answer across the Core boundary. Core must bind its actual current durable acknowledgement and exact installation credential to the saved API challenge. For delivery, require current confirmation for the exact registration, publication and device/channel generation at the provider handoff. An earlier positive registration receipt cannot serve as this confirmation. Core closes its local scope immediately on opt-out or unlink. API closes on missing, delayed, stale or invalid confirmation and records revocation durably when it receives it.

Test local retirement after the last successful status check and before API commit or provider handoff, with the retirement message delayed or lost. The API must reject if the current confirmation is unavailable or refused. A delivery already handed to APNs is outside the scope of cancellation. The live integration must identify and qualify the ordering point between authority confirmation and handoff before claiming that concurrent unlink blocks an in-flight operation.

For the first WidgetKit grant, Core can send the fresh confirmation outbound on the existing installation credential. No inbound callback to private HA is needed. The proposed shared fixture `qualification/native-push-mvp/widget-currentness-vector.json` contains the ordered UTF-8 JSON bytes, SHA-256 digest, synthetic Core public key and P-256 signature for exactly one `POST /v1/push/native/enrollment/issue` operation. All fields are ASCII; use compact JSON without whitespace. The Core key thumbprint is SHA-256 of DER SPKI, and the signature is fixed-width 64-byte `r || s` encoded as unpadded base64url. The vector binds the API-reserved registration ID and the digest of the canonical grant request, excluding the signature envelope. It is a cross-language fixture, not a live credential or a grant. The grant request and delivery wire are separate: the issue signature can never authorize a publication or provider handoff.

## Durable acknowledgements and order

1. Ordinary pairing completes. Core finishes the installation credential bootstrap and verifies durable storage before it captures the positive pairing witness. Core then retains the committed, current PairJournal acknowledgement for the exact runtime, original paired credential, config entry and auth generation. It checks currentness before requesting the API challenge, before handing the transcript to the paired Apple host, and again before forwarding the witness. A `/pair` success, `setup_pending` response, status read or restored local acknowledgement cannot replace this check.
2. The API reserves an opaque `api_installation_id` for the exact first-key operation and saves its one-use challenge against the current `install_credential_id`. The proposed `key/challenge` response carries `contract_version`, `operation_id`, `api_installation_id`, `install_credential_id`, `api_audience`, `challenge_id`, `challenge_nonce`, `expires_at_ms` and `expected_key_revision: 0`. A reservation carries no key or push authority. The authenticated HA response passes the same challenge and transcript to the Apple host.
3. Apple proves the transcript under the approved App Attest scope. Core supplies proof of possession of the exact Core key. For a fresh principal the API verifies both against the original saved challenge and checks the current installation credential, original pairing commitment, deadline and expected key revision at commit. The transaction consumes the challenge and creates the first active key together.
4. Only successful commit and exact readback produce the central `key/register` acknowledgement. It carries `contract_version`, `operation_id`, `api_installation_id`, `install_credential_id`, `pairing_generation`, `registry_generation`, `key_revision: 1`, `core_key_thumbprint`, `transcript_sha256`, the original `expires_at_ms` and `state: registered`. The API assigns `registry_generation` to the registry lineage. It is distinct from the opaque Core pairing generation and from the key revision within that lineage. Core accepts the acknowledgement only against the same original PairJournal record. Checking status can disclose the same receipt under proof of the same key within the original lifetime. An unresolved outcome stays closed.
5. An explicit device/channel opt-in is a separate operation after key registration. Issue a purpose grant only against the acknowledged registry generation and current key revision, original pairing, requested target and that device/channel's current consent generation. Key registration and its status disclose no push grant.

### Installation credential persistence

The existing Core `PairRegistration.current()` captures the identity of both `entry.data` and `entry.options`. The first successful `async_ensure_install_token` invokes `_persist_install_settings`, which replaces the options mapping. Its return alone supplies no durable readback. Capturing a positive pairing witness before this update would immediately invalidate it. Legacy push registration currently calls the bootstrap helper on demand. Native key enrollment must obtain and persist the installation credential as part of the original authenticated pairing flow, before the positive witness and independently of push opt-in.

The proposed sequence is to retain the still-current original pairing attempt while bootstrap is pending, verify the exact installation credential after the authorized durable write, then capture the current PairJournal acknowledgement and request the central challenge. If Core chooses a continuation across the options update, it must be limited to that exact authenticated bootstrap attempt and the expected settings change, while preserving the original runtime, paired credential, owner/device, PairJournal generation and original deadline. It cannot retake a generic options snapshot or create a replacement pairing acknowledgement. Ordinary options replacement, status, setup-pending responses and restore remain closed.

The API binds the challenge and key commit to the exact active `install_credential_id`. Replacement or revocation during the proof invalidates that operation. A retry or status read can return only the original durable outcome and cannot extend the deadline or revive a retired acknowledgement. Test a fresh bootstrap before capture, a credential replacement after capture, and unrelated options changes, retirement and restore during the original attempt.

The verifier accepts only a server-selected tuple of Apple team and bundle ID, platform, App Attest environment and permitted launch category for the HA-dev pilot. It verifies the genuine Apple trust chain, relying-party identity, nonce and attested key. A challenge-bound assertion may reuse a previously qualified host key only with its independently verified app/key scope and counter checks. The claimed client platform, APNs environment and key presence do not select a proof kind. The attested host app and proof of the exact widget or other delivery target are separate. The Core key proof uses its own domain and binds the same transcript hash, challenge, method and registration path.

## Independently authorized restore

Restore stays closed until an external authority and its verifier are selected. A current trusted Core key can authorize routine replacement under the existing lineage and expected revision. If that key or its trusted currentness is unavailable, recovery requires a separate, short-lived signed witness from the independent restore authority. The witness binds the original central principal, prior and current registry generation, prior key revision, current authorized pairing, new key thumbprint, fresh challenge, audience and expiry. It must be validated against current authority outside the restored snapshot. A backup, old journal acknowledgement, caller-supplied HA ID or legacy bearer cannot supply this decision.

Verify the replacement key's possession, consume the restore witness and challenge once, advance the registry generation, and retire the previous key and dependent grants in one commit. Keep the old lineage and receipt for audit and replay rejection. No delivery resumes from restored settings. Obtain new explicit opt-in for each affected physical device and channel under the new registry generation.

## Proposed API routes and proof

Use POST for every route below, with the existing per-installation bearer and strict JSON. Route names are proposed and unmounted. Every signed statement binds protocol version, method, path, environment audience, original installation and pairing generation, operation ID and API challenge. Sign using P-256 over the agreed canonical encoding. Return no-store responses. Keep assertions and credentials out of shared logs.

| Route | Request and authority | Result |
| --- | --- | --- |
| `/v1/push/native/key/challenge` | Installation bearer, operation ID, requested key thumbprint and pairing generation. No key is trusted at challenge creation. | A short-lived single-use nonce bound to that original request. |
| `/v1/push/native/key/register` | Challenge plus new key proof of possession and the attested fresh pairing witness above. Replacement additionally requires the active key and expected key revision. | Exact key ID, revision and active status. A changed key or pairing never replaces a prior binding implicitly. |
| `/v1/push/native/enrollment/challenge` | Current installation and registered Core key, operation ID and exact device/channel/role/target coordinate. | Short-lived nonce scoped to the action and original deadline. |
| `/v1/push/native/enrollment/issue` | Current Core-key signature on the explicit original opt-in, challenge and full coordinate. Verify purpose key possession and the separate Apple proof when the role requires it. | One bounded purpose grant using the existing role-specific issuer semantics where applicable. Return a credential only on the original issuance response. |
| `/v1/push/native/enrollment/status` | Current installation and a fresh Core proof for the exact operation and scope. | Original operation outcome and expiry. Never return or mint a credential from status. |
| `/v1/push/native/enrollment/revoke` | Current Core authority signs opt-out or unlink with the expected scope and generation. Revocation does not require the target still to be opted in. | Durable revocation of the scoped grant, capabilities and registrations. Retain tombstones and audit references. |

Commit checks must bind the exact active install credential, key revision, pairing/consent generations, operation, nonce and original deadline to the mutation. A preflight followed by an unguarded write is insufficient. Consume a challenge at most once. Exact idempotent retries return the stored outcome without new credentials or a longer deadline. Conflicting operation ID, scope, target, key or revision returns a conflict. An ambiguous response goes through status. Re-enrollment requires fresh authority and proof. A revoked generation never reopens. Loss of the Core key requires the independently verified recovery path, not a fresh legacy bearer.

Opt-out retires only the selected device/channel. Device unlink retires that device's channels. Owner or installation retirement can retire all grants in its own scope. Dispatch must recheck the same scope immediately before provider handoff and preserve existing provider replay rules.
