# Private first-enrollment category policy

The existing private custodian native-policy endpoint accepts the exact v2 single-category policy unchanged. Its new v3 profile, `host_wake_apple_properties_attestation_v3`, replaces `launch_validation_category_b64` with `allowed_launch_validation_categories_b64`: an explicit nonempty, unique, numerically ascending array of at most four canonical base64 UInt32 little-endian categories. Only the already supported categories 2, 3, 4 and 5 are structurally accepted. There is no default list, wildcard, automatic v2 conversion or actual category inferred from APS, development signing, an ordinary app launch or a local key file. Mixed-profile fields are rejected. The receiving protocol version, public native challenge/completion/status wire and API-selected proof kind are unchanged.

This is a custodian's bounded first-enrollment allowance, not evidence of a category. The actual Apple verifier checks the signed property against that saved set and returns the observed category only after all existing Apple path, RP-ID, nonce, key identifier, AAGUID, bundle-version, receipt and fresh signed common-status checks succeed. The source makes an independent copy of the policy set before cryptographic awaits. No caller CA, unsigned category hint or synthetic verifier result becomes native authority.

The separate opaque first-attestation receipt binds the observed category to its original job, key and policy. The guarded D1 transaction persists the existing assertion-properties v2 JSON with exactly that one observed category. The original v3 custodian policy remains immutable. Later assertions require the exact stored category; another category from the initial set does not qualify. Actual current enrollment resolution also checks saved assertion app/build and membership against the original policy. The key-insert trigger independently rejects assertion policy app/build/category inconsistent with the saved custodian policy. Key uniqueness, original claims, counters, capacity, current principal/operator/child state, receipt status freshness, withdrawal and terminal UNKNOWN semantics remain owning.

The original signed iPhone40451 artifact-inspection receipt and its environment receipt establish recorded artifact/signing facts. They do not establish the App Attest signed category. No actual custodian category set, native key, installation principal, registration, deployment or native SDK action is supplied by this source. Source-open and additive D1 execution remain separate concrete reviewed operations. The strengthened key-insert trigger requires its new exact code pin and corresponding later deployment/readback plan; an old remote trigger is not silently accepted.

One installed native key can support later separately admitted original children while its existing policy, status and target remain current. Each child retains its own challenge/proof/register/credential/deadlines. A child prepared as attestation before a different child enrolls the key cannot switch to assertion. Content-free APNs hints carry no surface or Session authority. No combined surface registration or cross-surface promotion is introduced.

Qualification distinguishes ordinary parsing/crypto/D1 source tests, a separately isolated trusted-kernel MODEL suite, and packaged/root composition tests. The new D1 corruption controls use modeled Apple evidence and actual D1 transactions; they do not prove genuine Apple enrollment. Their old-guard counterexample is retained separately. Historical source maps and prior build evidence remain immutable; an exact five-file delta binds current compiled runtime inputs, without activating any operational gate. No UI or en/nl/de/fr/es translation changes occur.
