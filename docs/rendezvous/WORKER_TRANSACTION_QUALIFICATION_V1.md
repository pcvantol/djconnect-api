## Creation boundary and storage

A **trusted future server allocator**, before awaits, creates an immutable
descriptor `{id,createdAt,expiresAt}`: random UUIDv4 and original120s deadline.
It must choose a new ID per transaction, route deterministically to that ID's DO
and retain the same descriptor for a retry. The internal create method verifies
the namespace/object binding and exact deadline before and after async framing,
hashing and alarm work. It cannot overwrite an existing row or renew a deadline.
The first cleanup alarm must be confirmed before inserting any row. Create has
one in-flight operation; a repeated committed create conflicts rather than
recovering its QR secret (only its commitment was stored).

After purge and restart a replay of the original descriptor is expired. There is
no permanent marker/denylist and **no intrinsic prohibition against a trusted
allocator violating its contract by retimestamping an old ID**. Public callers
must never supply descriptors, IDs/object names or timestamps for create. The
public allocator/controller and its admission proof are not implemented here.
Inspect/poll/submit/consume/cancel never create missing state. No missing request
automatically initializes or revives a transaction.

One finite row holds original descriptor/generation, public browser key/thumbprint,
separate SHA256 claim/QR commitments and state. A32-byte CSPRNG QR capability is
returned only in the bounded raw JSON QR. The claim secret is generated by the
browser; only its supplied commitment is stored. Incoming claims/QR capabilities
are hashed and compared as32-byte buffers using the verified native Workers
`crypto.subtle.timingSafeEqual` inside the final storage transaction. There is
no custom JS constant-time claim or new cryptographic protocol.

Pending->ready stores the ciphertext plus a minimal immutable operation/request
digest. Ready->consumed releases the envelope exactly once and erases it before
returning. Pending/ready->cancelled erases it without release. Both terminal
transitions also erase the browser public JWK; retain only original binding,
commitments, deadline, historical receipt and bounded poll metadata until expiry.
No raw QR/claim, Apple key ID, clientData, assertion or plaintext HA URL enters
this transaction row. Linkable commitments/thumbprint/digests remain metadata,
not anonymity. Alarm deletes the entire expired row; request-time expiry is
authoritative even if alarm is late. Failed cleanup throws for provider retry;
provider scheduling/monitoring/physical deletion/backups are not qualified.

## Submit authority, races and retries

Only the facade is an intended DO export; it contains the plain engine in a JS
private field. Default authorizer derives the canonical key address using the
existing development/policy tuple, fixed private namespace and real
`ENROLLMENT_COORDINATOR.authorize` RPC. It accepts no request-controlled grant,
counter, boolean verification or namespace selector. The separate temporary QA
subclass uses the existing separate software-enrollment binding. Its constructor
choices and fault-injection closures are server/test seams, never RPC fields.

Submission copies the complete closed, bounded typed input before awaits. Its
server-computed **internal** SHA256 digest covers an unambiguous fixed JSON array
of protocol/action and every exact input string/number. It is not a claim about
raw HTTP JSON byte canonicalization. Raw request parsing/duplicate rejection and
public request bounds remain controller work. ClientData, assertion and envelope
string equality are exact; altered values cannot recover the receipt.

The structural parser uses the **saved browser thumbprint**. The coordinator's
own expected request digest is independently calculated using its existing exact
key-address/action/clientData/assertion tuple. Private authorization must match
the original transaction, generation, thumbprint, envelope digest, expiry,
operation and request digest. The existing internal authorization response now
also returns its already saved `admittedAt,keyExpiresAt`; no public wire field,
counter predicate or deadline changes. Final synchronous SQLite checks require
the original absolute lease, at most5s from admission and capped by key and
transaction deadlines. No await occurs between that check and ready commit.
Only one submission verifies at a time per engine; concurrent overload fails
closed and may retry within the original deadline.

Cancel/consume linearize in that same transaction store. A counter burned before
a failed ready commit does not make ready. Exact retry may finish only within
the original coordinator lease; afterward it needs a fresh challenged higher
counter while still pending. After a ready commit, identical capability-bound
retries return **historical acceptance only**, even after consume/cancel or key
revocation; no new coordinator lookup, state revival or envelope release.
Different operations cannot replace ready. Lost consume response requires fresh
QR after authenticated consumed status; it cannot recover ciphertext.

As previously reviewed there is no cross-DO atomic key revocation. A previously
returned authorization may still commit within its original bounded lease after
revocation. Earlier key expiry/revocation prevents fresh authorizations; later
revocation does not recall an already ready/consumed address. Separate HA display
admission remains the authority for actual screen access.

Poll is claim-authenticated, contains only state/deadline/retry_after_ms and
enforces the existing2s interval/60-poll ceiling. Other global allocations, IP,
challenge and invalid-attempt budgets, streamed payload/Origin/CORS checks remain
separate API work; this is not overall abuse qualification. All responses/errors
are fixed typed results without request/body logs or destination fetches.
